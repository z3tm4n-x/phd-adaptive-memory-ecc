# Договор одного сервиса EV30/OFF

Это условный проектный договор, а не измеренная реализация. Общий вход
приложения/объёма/срока/epsilon закреплён в `sources.json`; ENV из v4
не используется. Устройство/AC — принятый пример #206/PR221 и его
[адресная передача](https://github.com/z3tm4n-x/phd-adaptive-memory-ecc/issues/186#issuecomment-6342136613).

## Последовательность и окна

Один сервер, один SRAM-интерфейс; обращения в true SI ns:
read `100000+q*1000020`, write `600000+q*1000020`, слово `5q mod131072`.
При поступлении до T запланированная работа выполняется полностью даже при
ответе за T; после первого превышения A подсчёт и работа не прекращаются.
Дополнительных scrub/startup-проходов нет. Read возвращает результат полного
decode без repair; write наблюдает старое слово, декодирует, кодирует новые
полезные 32 бита и пишет все три x16 адреса. Неприменяемые ERR не управляют
периодом, cuts/пакеты адаптивного наблюдения не создаются. Ошибочный decode
не даёт бесплатного прерывания, повторов или раннего выхода в расчёте цены.

После входа 320+80 нс запрос обслуживается при первой готовности; ожидания
кадра нет. В c включены dispatch/квантование старта/lock/адресная подготовка,
захват/статус/завершение и любые служебные действия, ещё не входящие в beats,
decode, encode и release. Все три адреса `3*w+[0,1,2]` блокируются до release.
В начале первой read адрес должен быть валиден до/одновременно с CE/BE;
предлагается зарезервировать первые 8 нс из c на подготовку перед включением
CE/OE. Скосы должны сохранять этот порядок, как требует прим.26 стр.8.
Остаток c оплачивает остальные действия, распределённые по транзакции.

Read-beat: следующий адрес на начале 64-нс цикла, выборка на56 нс,
оставшиеся8 нс удерживают выход перед сменой адреса/снятием OE.
Первое чтение включает CE/OE/BE доступ, последующие — address-controlled;
WE всегда HIGH. После трёх чтений OE HIGH, пауза32 нс, полный decode32 нс.

Write: после pre-read/release/decode следуют encode32 нс и три полных
64-нс цикла. На начале каждого адрес, данные, CE/BE уже активны/валидны;
WE LOW на8 нс, HIGH на48 нс, адрес/данные/CE/BE держатся до64 нс.
OE остаётся HIGH: это Figure7, а не OE-low WriteCycle3. WE-rise действительно
завершает write; CE/BE не должны деактивироваться раньше. После третьего
write контроллер отключает свой output и CE, сохраняет OE HIGH и ждёт32 нс
перед передачей интерфейса. BYTE=VCC, оба byte-enable активны.

Номинальные занятости без c: read `3*64+32+32=256`,
write `3*64+32+32+32+3*64+32=512`, init `32+3*64+32=256` нс.
Decode/encode — проектные бюджеты32, c — бюджет64 нс на каждую транзакцию,
включая init. Неизвестный WCET не превращается в измеренные64 нс.
Все эти интервалы резервируют интерфейс; скидки за перекрытие нет.

Для каждого интервала x: `x*0.99999-0.5 <= elapsed <= x*1.00001+0.5` нс.
Это условие общего clock/разности endpoint, не независимый J каждого beat.
При проверке отдельной AC-разности используется её собственная огибающая;
при суммировании всей транзакции J применяется один раз.

Общая служебная апертура768 нс начинается после ready, не является кадром
и не удерживает шину после фактического конца. Её нижняя длина767.49232 нс;
локальная цель80% =613.993856 нс. Полный write с c занимает <=576.50576 нс.
Полный ответ с выходом320+100 нс <=1396.50576 нс, ниже2400 и3000.
Минимальное расстояние между внешними запросами500000 нс; индукция от
пустого начального сервера даёт отсутствие очереди, поскольку даже ответ
заканчивается раньше следующего arrival. Никакой средней нагрузкой очередь
не подменяется. Необъявленный трафик других владельцев шины сюда не входит.

Endpoints: a — внешний arrival, R — ready после полного входа, S —
причинное взятие lock/начало E до pre-read, F — release ПОСЛЕ всех трёх
write, последнего hold и отключения выходного драйвера/паузы release.
Новый payload к F полностью записан; выдача команды ещё не является F.
ACK разрешён только после F, затем оплачены outbound/backpressure.
`a<=R<=a+400`, `R<=S<=F<=R+576.50576`,
`F<=ACK<=a+1396.50576` нс для write. Для read аналогично с320.5032,
полный ответ<=1140.5032 нс. Никакого раннего ACK до E-release нет.

При fixed64/32 release общий номинальный предел для выбранного локального
запаса: `d+e+c <= 82744688/500005 =165.487721122788...` нс.
При d=e=32: `c<=101.487721122788...`; сверх бюджета64 остаётся37.487721...
номинальных нс. Дополнительные decode/encode/служебная блокировка расходуют
ОДИН предел. Hard-апертура допускает c<=254.984650..., но её использование
уже теряет локальный20%-ориентир. Запас ответа1003.49424 нс до2400 не разрешает
обойти более тесное локальное условие. Плата не оплачивается этим остатком
автоматически: нужны отдельные нижеследующие интервальные неравенства.

## Инициализация, цена, исключения

До t=0 оплачены W encode и3W write; контроллер/release также оплачены.
Активный prefix <=42.0089954304 мс. После установленного стабильного питания
добавлен выбранный wait256000 нс, нижняя длина255996.94 нс >200000 из
прим.7; elapsed до конца init <=42.2649984904 мс плюс неизвестный boot.
Время ramp/stabilization и выполнение условия ramp из прим.7 не установлены.
Верх от включения питания поэтому UNKNOWN. Wait не выдаётся за SRAM-busy,
но его питание/CPU/idle входят отдельными неизвестными в полный ресурсный вектор.
Последовательная инициализация не доказывает одновременно clean в t=0;
clean/pending=false — сохранённая условная предпосылка, физический escape UNKNOWN.

Средняя шина — полная занятость каждого начатого до T обращения + весь init,
делённая на T. Это консервативно оплачивает pending за концом T.
Любой рабочий1мс: пересекающие его операции имеют arrivals в расширенном
окне длиной1мс+D. На поток максимум2, суммарно максимум3 по spacing500000;
верх полной работы — два write и один read =1473.51472 нс. Поэтому
пик <=0.147351472%. Это достаточная огибающая, не точный максимум.
Init лежит до0 и предъявлен отдельно: его плотная шина не соответствует
рабочему1мс-ограничению и не скрыта в нём.

В цене `c_read,c_write,c_init` не пересекаются с beat/decode/encode/release.
В outputs даны их коэффициенты и срез c_i<=64. Дополнительные
`B_extra_mean/B_extra_1ms` и задержка блокировки — отдельные параметры;
при наличии такого трафика нужно одновременно выдержать шину, ответ и
апертуру, а не вычесть только среднюю цену. CPU/LUT/BRAM/память/джоули
остаются вектором; ROM из принятого кодека — одна реализация, не lower всего t2.
Сохраняются 4 байта полезной нагрузки на read/write и неизвестные headers.

All-history пределы длительности — отдельная детерминированная предпосылка
исполнителя на ВСЕХ учитываемых историях, в том числе после A и на G^c.
Они не следуют из малой вероятности исключения. OFF не включает скрытого
fallback/повторного scrub даже после A; ограниченный c содержит обычное
завершение/статус, а не необъявленную рекурсию retries. В реальной аппаратуре
неограниченное зависание не покрывается этим конечным вектором цены.
Для его включения нужен отдельный конечный предел удержания/восстановления
и численная цена, либо физическая полная цена остаётся UNKNOWN.

Для применения прежней геометрии #196 нужны причинные a<=S<=F<=a+D,
охват каждого слова и E: до A не создавать ошибку, удалить старые рождения,
оставить лишь рождения не ранее S. Последовательные three-beat snapshot и
lock не доказывают физический E. Моменты/метки EV30, lifetime среды,
инициализации и E/исполнения UNKNOWN; старые per-bit и Delta6e-6 не переносятся.
Перекрывающиеся исключения оплачиваются один раз обоснованной общей границей;
непокрытые не становятся нулевыми. Никакой новой Q здесь нет.
