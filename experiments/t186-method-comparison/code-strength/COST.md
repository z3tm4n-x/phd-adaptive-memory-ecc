# Полная цена и параметрические пороги

Численные коэффициенты теперь рассчитаны в `outputs/results.json`, одна таблица
находится в `outputs/table.md`. Вход инженерно согласован, конкретная подпись
#196 к сервису/строкам ожидается. Удельные физические цены не измерены.
Ниже общий бухгалтерский договор; уточнения основного среза — [SERVICE](SERVICE.md).

## Единицы работы

Для каждого варианта i считаем за **весь T**, также после первого превышения A:
S_i — начатые контрольные чтения, R/W — прикладные read/write, E_i —
исправления контрольного чтения, H_i — исправления прикладного read.
В основном срезе **H_i=0 по определению общего read без write-back**.
Нулевое число scrub-repair не предполагается. N0=W_words инициализированных
слов до t=0 оплачиваются кодированием/записью отдельно и в цене /T.
Наблюдаемая write/RMW уже включает исправление старого снимка в новый образ:
второй фиктивной исправляющей записи нет. Тогда

```
Ndecode_i = S_i + R + W
Nencode_i = W + N0
Nread16_i = 3 (S_i + R + W)
Nwrite16_i = 3 (E_i + H_i + W + N0)
```

Это E-сервис. Для U нужна отдельная строка договора с E_i=S_i на каждой
истории; нельзя незаметно поставить U только одному сопернику. Для одинакового
приложения количество предложенных payload одинаково. Read выдаёт 4 байта,
write принимает 4; заголовки/адрес/подтверждения/буферы учитываются дополнительно.

Операция кодека задана явно: синдром Hx, адресный доступ к ROM `syndrome →
(valid,error_mask)`, XOR исправления; encoder — систематическая линейная
матрица T187. Коррекция кодового образа XOR-маской не требует нового encoder;
прикладное изменение данных требует. Прямое число двухвходовых XOR приведено
для несокращённых деревьев без общего использования подвыражений. Это один
реализуемый логический вариант, не нижняя цена оптимального кодека, не LUT
и не measured WCET. Python-петли служат функциональным эталоном, не таймером.

При чтении после A выбранная реализация может дать ошибочное исправление,
но расчёт продолжается. На всех историях E_i<=S_i, H_i<=R: это ресурсный верх,
не оценка числа правильных исправлений. Ожидаемые E_i/H_i требуют отдельной
оценки с ценой плохих историй; они не подставляются равными нулю при пустом trace.
Полное списание начатой операции, включая pending за T, даёт консервативный
верх цены до T; точная занятость обрезается границей T и обозначается отдельно.

## Вектор цены

Для времени одного такта обмена r/w, времени разворота u и числа разворотов Z_i:

```
B_i = Nread16_i*r + Nwrite16_i*w + Z_i*u
      + Ndecode_i*d_bus,i + Nencode_i*e_bus,i + Ndecision_i*c_bus,i
C_SRAM,i = B_i / T
```

0<=d_bus<=d_decode, 0<=e_bus<=d_encode. Если кодек блокирует общую шину на
весь расчёт, оба равенства достигаются. Если обмен перекрывается с расчётом,
это надо подтвердить календарём/блокировкой/памятью очереди, а не объявить
задержку нулевой. `c_bus` — только дополнительная занятость контроллера,
не уже посчитанные read/write/кодек. Развороты не выводятся из одного среднего
трафика: их число задаётся реальным общим календарём.

CPU-координата: `sum N_action*c_action/T`; действия cut, capture, обработка
записи, решение, timer и app-dispatch имеют непересекающиеся области.
Кодек здесь аппаратный; при программном варианте его работа переносится в
CPU, а соответствующая аппаратная статья удаляется, без двойного счёта.
Полезный/служебный канал: `4(R+W)+headers+32*Nsource_records+cut_headers`.
Потерянная запись оплачена на стороне источника, незавершённая не исчезает.

Энергия отдельно: сумма динамической цены каждого вида работ, полного
транспорта и idle_power*T. Память отдельно: кодовые данные, плотная ROM,
регистры кодека, 128 КиБ frozen transport + 64 байта loss-state **только в
адаптивной строке**, состояние политики и payload buffers.
LUT/BRAM, частота, размещение и потребляемая мощность пока UNKNOWN.
Логические ROM-биты не равны целочисленному числу блоков FPGA.
Постоянные схемы не оплачивают ненужные cuts/ERR-records. Их аппаратный таймер,
выдача сервиса и общая нагрузка приложения остаются отдельными статьями.

CPU, занятость SRAM, LUT/BRAM, память и джоули **не складываются** без явных
весов. В этой поставке таких весов нет. Возможен векторный/Pareto вывод либо
выбор по одной заранее названной координате при остальных ограничениях.

По [адресному заключению #196](https://github.com/z3tm4n-x/phd-adaptive-memory-ecc/blob/d47bf85cbce1342fd325198cf048f2ce837c4d8b/experiments/comparison-foundations-20261018/review-20261022/REPORT.md)
дополнительные подтверждения GAP/RESTORE с новым G оплачиваются отдельно:
`N_veto_extra` — дополнительные действия помимо base capture, а
`theta_veto_extra` — верх добавочной ожидаемой доли FAST. Для ценового
сертификата суммарная доля ограничивается `min(1,theta_ordinary+theta_veto_extra)`.
Это два разных входа: частота уведомлений сама по себе не определяет
время FAST без временной геометрии. Число эпизодов их не ограничивает.
При неизвестном бюджете нельзя поставить theta_veto_extra=0; остаётся
весь диапазон [0,1] и край всегда-FAST. Член CPU/энергии extra-veto
исключает уже оплаченную capture/record работу. Обработчик сохранён;
старый upper 17.4843% и выигрыш 1.761x для этой области не используются.

## Допустимая задержка и порог смены выбора

Обнаружение на полном read: `3r+d_i`; исправление добавляет `3w+u`.
RMW: `3r+d_i+e_i+3w+u`. Время ответа дополнительно содержит реальную очередь,
входную/выходную доставку и backpressure. Старые 3900 нс — условный бюджет
обработки готового пакета; он **не** измеряет внешний декодер. Его публикация
ERR и новые длительности операций должны войти в проверку общего endpoint.

При заданных остальных слагаемых предел задержки d2 — минимум остаточных
ограничений, например:

```
d2 <= deadline_app - (queue + ingress + 3r + e2 + 3w + u + outbound)
d2 <= [T - Nencode_2*e2 - other_codec_busy] / Ndecode_2
```

Первое проверяется на худшем допустимом запросе; второе — только средняя
необходимая пропускная способность одного последовательного кодека.
Оно не доказывает deadline/отсутствие переполнения. Дополнительно нужны
условия полного E-окна для Q, минимальный слот, пик `busy(I)/|I|<=0.8`
для **каждого** окна 1 мс и ресурсы буферов. Отрицательный остаток означает
недопустимость этой точки; его нельзя обрезать до положительного предела.

Для одного ресурса пишем полную цену `C2=A2+b2*x`, `Ca=Aa+ba*x`, x>=0,
с непересекающимися членами. При b2>ba:

```
C2 < Ca  <=>  0 <= x < (Aa-A2)/(b2-ba).
```

При обратном знаке меняется сторона неравенства; при нулевой разности
решают свободные члены. Отрицательная точка пересечения не создаёт
положительной области выгоды. В частности, при x=d_bus,2 и фиксированной
занятости шины адаптивного варианта предел равен
`(B_a - B2_other)/Ndecode_2`; B_a и B2_other измеряются в наносекундах за T.
Если d_bus,2=0 из доказанного перекрытия, границу определяют полная задержка,
кодек/CPU/память/энергия и ограничения, а не нулевая цена декодирования.

Численный порог, совместный сервисный предел и пересчёт Q/corrections на нём
опубликованы в `conditional_bus_comparison` результата. Сравнение двух верхов
даёт лишь порядок бюджетов; здесь дополнительно приведён lower цены именно
выбранной mandatory-опоры адаптации, **не** всего постоянного класса.

Для этой первой таблицы E Nrepair <= F_parent + U_Q Nhard. До глобально плохой
истории ремонт списывает хотя бы одного ранее не списанного родителя; после
неё оплачивается весь hard-поток. Adaptive ordinary price покрывает каждый
из <=2 ERR/parent полной длинной hold-полосой: наблюдение позднего рождения
внутри E и его повтор следующим E. Обычный app-read не выдаёт ERR/G.
Запись RMW выдаёт ERR при предмодификационной проверке, но делает только один
full write. В цену плохих историй входит новый coupling-upper T196(7), а
не более низкий физический коэффициент или прежний full38 результат.

Срез v=0 означает отсутствие **дополнительных** новых подтверждений G сверх
обычных false/loss/recovery условий. Это не оценка физического канала.
При произвольном v действует min(hard,ordinary+kappa_v*v). В JSON сохранены
добавочные коэффициенты decodes/beat/records/timer/extra-veto; CPU и энергия
уведомлений не исчезают при насыщении FAST. All-history счётчики/поток также
ограничивают каждый физический ресурс, когда требуется более тесный верх.

Энергетические коэффициенты означают **непересекающуюся добавочную** цену
работы: read/write beat, codec, управление, транспорт, idle. Например,
энергия scrub-controller не должна ещё раз включать уже оплаченную энергию
SRAM/decode. Аппаратный кодек не списывается вторично в CPU. Размер ROM
не равен measured BRAM/LUT; ограничение ресурса с неизвестным cap — UNKNOWN.

SRAM-числа таблицы — ядро плюс явные B_ctl_avg и B_ctl_1ms. Дополнительное
controller bus-work обязано поместиться в свободные окна и не сдвигать E,
app-grant, ready/delivery. Для существующего адаптивного transport остаётся
условный пакетный срок3900нс; цена record/cut/policy должна удовлетворять
этому сроку, а не только средней загрузке CPU. Нового транспортного решения
или измеренного выполнения этого бюджета не заявлено.
Для доказанного предпочтения по реальным ожидаемым ценам нужно
`upper(C2)<lower(Ca)`; для выигрыша против всего постоянного класса — его
применимый class lower. Равенство sufficient-цен или старые коэффициенты
20x/1.761x/2.8x этого не обеспечивают.

## Условие — основание — проверка — последствие нарушения

| Условие | Основание | Проверка | Последствие нарушения |
|---|---|---|---|
| Один полезный объём, x16 и r(t) | Предлагаемый общий JSON | Целое размещение/экспозиция | Сравнение кодов несопоставимо |
| Весь кодовый образ и маскирование padding | T187 H и явная карта | Все позиции, 45364 направленных исправления | Меняются код/сервис/область Q |
| Новый n39 сертификат и E/app | Требование #196, T187 не покрывает случайный календарь | Адресная подпись к входу/формулам | Адаптивная Q неизвестна |
| Физические группы и direct имеют основание | T187 (1)–(3) | S3, 1+2/2+2, общий lifetime budget | Синтетический эталон не физическая точка |
| Приложение и RMW полностью оплачены | Полное старое слово до модификации | 3 read + 3 write, decode/encode, headers | Цена и ресурс занижены |
| Цена до T, включая A/pending | Общий критерий #186 | Отдельная направленная проверка | Нет полной цены |
| Известны типы ценовых оценок | Upper/lower/точная история различаются | Проверка пары перед выводом | Нет доказанного выигрыша |
| Реальные времена и память укладываются в сервис | Условие теории, не измерение | Предел задержки, peak, очередь, размещение | Достаточная Q неприменима |
