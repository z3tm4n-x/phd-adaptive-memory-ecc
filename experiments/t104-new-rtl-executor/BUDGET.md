# T104: полный условный бюджет и передача для пересчёта

Решение Ивана в #104 от **06.10.2026**, вариант 2. Исходная поставка
`6e745aa7423a33220180ff6059073348fee7e83a` сохранена побайтно, кроме актуального
README. `TIMING.md`, старые config/code/test/JSON — история первого шага.
Сейчас выполнен инженерный бюджет; основной RTL и В/Г не начаты.
Новая научная версия ещё отсутствует. А и T95 не подгоняются под эти числа.

## 1. Что зафиксировано до расчёта

Метрика — полное время владения общим интерфейсом от grant/lock до безопасного
разрешения следующего grant, включая разворот DQ, захват ERR и освобождение.
Для прохода складываются времена **исполненных** посещений, включая после
скрытого отказа. На конечном горизонте считается пересечение занятых интервалов
с горизонтом, хвост pending не теряется. CDC до grant/после release входит
в задержку запроса, но не прибавляется к занятому времени интерфейса.
Работа канала/управления на этом интерфейсе оплачивается отдельно X;
CPU-время не складывается с процентами интерфейса.

Сравниваются E (запись только по ERR) и безусловная запись **на одном backend**,
с одним захватом/учётом ERR, запуском и освобождением. Соперник здесь —
техническая контрольная циклограмма, не оптимальный постоянный метод.
Для будущего постоянного E нужны отдельные допустимый период и нижняя цена.

Кандидат исполнения: один CY62167GE30-45, ×16, оба byte enable, OE-high write;
один alias известного внутреннего слова. Все обращения сериализованы глобальной
блокировкой интерфейса. FPGA, плата и процессор **не выбраны**.
Таблица ниже — проверяемые **проектные требования**, зафиксированные
в `budget_config.json`, не сведения об AC701 и не измеренные задержки.

| Величина | Проектная граница | Что должно её подтвердить |
|---|---:|---|
| Core | 4ξ, номинально 250 МГц | Реализация с STA; ξ∈[0,99999;1,00001] нс — прежний постоянный масштаб |
| Ошибка каждого фронта относительно этого масштаба | ≤0,25 нс, разность двух ≤0,5 нс | Общая граница skew/jitter; это не накопительный дрейф и не новый статистический бюджет |
| Выход регистра/IO/трасса до входа SRAM, любой адрес/control/DQ | ≤4 нс | STA/плата при напряжении, нагрузке и температуре; межсигнальный skew до 4 нс |
| Возврат от SRAM до регистра захвата | ≤2 нс | Более медленный из DQ и ERR, включая трассу/вход IO |
| Setup / hold регистра захвата | ≤1 / ≤1 нс | Библиотека, STA, совместный захват DQ/ERR |
| Решение ERR/арбитр/телеметрия | ≤3 нс в одном core-периоде | Совместное исполнение; работа команд не может добавлять неучтённый stall |
| Отключение драйвера FPGA и установление линии | ≤6 нс | IO disable + трасса/settling; не нулевой turnaround |
| Dispatch до launch | 1 core-период | Подготовленный адрес/alias; адресная арифметика должна укладываться или выполняться заранее |

Нижний предел распространения 0 используется только консервативно в проверке
скошенных фронтов; это не подстановка нуля вместо неизвестной верхней границы.
Все физически неподтверждённые upper в JSON остаются `null`.
Требуются паспортные условия питания/температуры/нагрузки/скорости фронтов;
их соблюдение конкретной платой здесь не установлено.

## 2. Встроенная частичная запись: один внешний цикл

Повторно проверены существующие источники:

- Паспорт **002-20054 Rev.*F**, с.1,10,14; URL/SHA-256 в прежнем `config.json`.
  Сверена прежняя сумма `a7d9fa…ed1f`, просмотрены таблица и Fig.14.
- [AN88889 Rev.*C](https://community.infineon.com/gfawx74859/attachments/gfawx74859/NonVolatileRAM/1914/1/Infineon-AN88889_Mitigating_Single-Event_Upsets_Using_Infineon_65-nm_Asynchronous_SRAM-ApplicationNotes-v04_00-EN%201.pdf),
  §4.2/4.4/5.1, с.5/7/8; 623211 байт,
  SHA-256 `4fd1504873cd89fe73a2a68646cc159ff3b7804a1ee129261252d31eb60f17bc`.
  Это именно версия из T68, не Rev.*D из T50.
- Принятый [T68 contracts §4](../t68-v21-inputs/contracts.md).

AN описывает внутреннюю обработку полного 32+6 при одной записи выбранных
16 бит: чтение/исправление буфера, замена части, новый parity, запись целого
слова. Чтение выдаёт исправленную часть без writeback. **Инженерный вывод
из AN и паспорта:** внутренний путь включён в штатный внешний write cycle;
отдельного дополнительного tRC/45 нс к нему не предъявлено. Считаем один
внешний read и, при ERR, один внешний write, а не read+write+скрытый read/write.
В ×8 часть имеет 8 бит; произвольная запись новых 32 data — два ×16 либо
четыре ×8 обращения, что не является одним таким циклом.

Используемые pin-требования: read tAA/tACE/tDBE≤45, tDOE≤22, tRC≥45;
output disable≤18; write tWC≥45, tPWE/tAW/tSCE/tBW≥35, tSD≥25,
tSA/tHA/tHD≥0 (нс). Write end — первый завершающий control-фронт;
setup/hold проверяются относительно него. OE выключен до включения FPGA DQ.
Не складываем подряд tPWE+HZ+setup: ограничения могут выполняться совместно.
Схема OE-low из note34 не используется.

Успешный внешний цикл означает функционально завершённую запись к следующему
допустимому обращению. Точный момент изменения всех 38 ячеек и поведение при
попадании частицы внутри цикла из pin-таблицы **не следуют**. Для Q(T) это
прежнее условие сервиса/δ_svc, а не дополнительный нулевой интервал.
Условные полнота ERR (включая check), grouping и D* не квалифицированы заново.

## 3. Циклограмма и арифметика

Пусть J=0,5 нс — верх разности ошибок двух фронтов, q=4.
Для требуемого интервала L выбирается
`wait(L)=q*ceil((L+J)/(q*ξ_min))`.
Длительность от grant до release N тактов имеет условный верх
`B(N)=N*ξ_max+J`. Для запаса 10% заряд/резерв:
`C(N)=q*ceil((1,1*B(N)+J)/(q*ξ_min))`.
Этот резерв — верх для анализа загрузки и арбитража, **не искусственная
задержка release**. Интерфейс освобождается по фактической циклограмме.

| Событие от grant | Такт ξ | Без ERR | С ERR / безусловный comparator |
|---|---:|---|---|
| Lock всех alias, dispatch | 0 | Общий | Общий |
| Address/CE/BE/OE на выход контроллера | 4 | Read | Read |
| Достоверность на выводах SRAM | ≤launch+4+45 нс | DQ и ERR | DQ и ERR |
| Возврат + setup и захват DQ/ERR | 60 | Один согласованный снимок | Сохранить исправленные 16 data, alias, ERR |
| Решение/учёт ERR, OE↑ | 64 | Также CE disable | CE/BE и адрес сохраняются; lock/pending остаётся |
| SRAM и линия достоверно Hi-Z | 92 | **Release, следующий grant разрешён** | FPGA DQ drive + WE↓; следующий grant запрещён |
| WE↑ / CE disable | 132 | — | Завершение внешней записи; безопасно учтён skew обоих фронтов |
| FPGA DQ disable | 140 | — | Setup/hold завершены |
| Безопасный release/final ACK backend | 148 | — | Pending завершён, следующий grant разрешён |

Проверки дают, например, остатки ≥3,49944 нс до read capture,
≥3,49972 нс для SRAM→FPGA turnaround и ≥0,4996 нс для WE pulse.
Уменьшение каждого из этих интервалов на один core-такт нарушает соответствующее
достаточное условие. Полная таблица 27 остатков — `outputs/budget.json`.
Внешний read/write внутренний ECC уже включают; внешнего SEC-DED codec нет.

На ERR=1 нет очереди отложенных исправлений: глубина pending=1, исправление
немедленно продолжается внутри lock. Ни loss, ни команда/ERR другого источника
не снимает lock. **До решения и безопасного Hi-Z нельзя выдать grant даже
другому alias того же слова.** Глобальный lock исключает такой grant вообще.
Новая запись, принятая перед контролем, сначала завершается; контроль читает
новый образ. Новая запись после контроля получает grant только после release.
Offer/CDC-capture не являются accept/grant. ACK mailbox не является записью
в SRAM. Семантика принятой записи через committed skip остаётся обязанностью
будущего RTL; старые четыре регрессии А повторены.

| Операция | Верх владения интерфейсом, нс | Charge с 10%, ξ | Максимальное прямое блокирование нового grant |
|---|---:|---:|---:|
| E, ERR=0 | 92,500920 | 104 | 92,500920 нс |
| E, ERR=1 | 148,501480 | 164 | 148,501480 нс |
| Безусловная запись после read | 148,501480 | 164 | 148,501480 нс |
| Отдельный application read ×16 без inline writeback | 92,500920 | 104 | 92,500920 нс |
| Отдельный application write ×16 | 68,500680 | 76 | 68,500680 нс |
| Атомарный application read 32 data, два alias | 185,001840 | 208 | 185,001840 нс |
| Атомарный application write 32 data, два alias | 137,001360 | 152 | 137,001360 нс |

У application-write address/CE/BE/DQ выставляются на 4ξ, WE↓ на 12ξ,
WE↑ на 52ξ, DQ off на 60ξ, release на 68ξ. Одновременные address/WE
без guard не гарантируют tSA из-за skew. Для новых 32 data оба alias
блокируются на весь составной запрос; внутренний первый write не делает
второе внешнее обращение бесплатным. Если application read должен сам делать
inline repair, его максимум — **148,501480 нс на alias**, для двух —
297,002960 нс; политика приложения пока неизвестна. Таблица простого read
не разрешает скрыть эту работу. Записи приложения остаются вне области Q(T).

## 4. CDC, команды, очередь и совместное время

ERR захватывается вместе с DQ по timing SRAM; это не независимый двухтриггерный
синхронизатор ERR с потерей согласованности. Для предложений CPU и команд —
стабильный bundled payload, sequence/toggle и ACK, без побитового sync шины.
Ниже только достаточные требования на good event; синхронизатор не даёт
детерминированного абсолютного времени разрешения метастабильности. Отказы
должны входить в **прежнюю** δ_exec, без новой квоты.

| Путь вне memory lock | Условная граница | Что включено / неизвестно |
|---|---:|---|
| Request→домен памяти | 16,500160 нс | 4 core-периода: capture/sync и validation; требуется стабильность payload |
| Response→CPU | 40,500400 нс | 4 периода CPU при T_CPU≤10,0001 нс и edge±0,25 нс; процессор пока не выбран |
| Полная команда→проверенный shadow | 32,500320 нс | 3 core sync +4 validation +1 публикация; не цена вычисления правила/доставки монитора |
| Read16 от первого VALID до done при пустой очереди | 149,501480 нс | Включены оба CDC и release; нет чужих операций и backpressure по определению этого частного случая |
| Write16, те же условия | 125,501240 нс | Не общий предел задержки приложения |

Цена CPU/транспорта, MMIO X, backpressure и ожидание очереди **не равны нулю**:
их upper пока неизвестны. Нужен поток тех же полезных запросов с шириной,
атомарностью, частотой и всплеском; нельзя оставить старые 4% путём уменьшения
полезной нагрузки. Из work-envelope с *верхом* длительности 45 нс нельзя
вывести число запросов делением на 45 нс. Для count-envelope `N(u)≤b+ρu`
полезно достаточное `B≥ceil(b+ρ*D_offer_to_departure)`, где учтены CDC и удержанные
ответы. Старые диагностические b=8, ρ=2·10⁶/с и **доказанные впоследствии**
общие 3 мкс дали бы 14 мест; кандидат 16 не подтверждён без этого условия
и нового work/service расчёта. Без предела backpressure конечная очередь
не гарантируется. Ни overflow, ни снятый VALID не разрешают отменить pending.

Ранняя команда остаётся неактивным shadow с точным nominal `not_before`.
LOW/окна не расширяются; late/invalid ведут к S только для будущих решений.
Alarms сначала отзывают active и shadow; уже committed skip/операции не меняются.
Для **сравнения** с прежним deadline при J=0,5 нс весь post-window путь
с запасом 10% должен укладываться в 0,999999999445… с, а путь до mailbox —
в 0,999999966945… с после вычета 32,500320 нс. Новые сроки/lead/lease должен
проверить теоретик с новым календарём, а не использовать эти числа как новый LOW.
Накладные расходы расписания, проверки команды, арбитража и телеметрии должны
совместно выполнить dispatch/logic/I/O требования без stall обязательного слота;
ресурс X обязан покрывать их работу на общей шине, в том числе восстановление.

## 5. Занятость, календарь и скользящий пик

Для W=524288 посещений и K∈[0,W] исходов ERR:

`busy_pass ≤ W*R + K*(E−R)`, где R=92,500920 нс, E=148,501480 нс.

| Условие | Верх занятого времени прохода | Экономия против безусловной записи |
|---|---:|---:|
| K=0 | 48,497122345 мс | 29,360421601 мс, 37,71044% |
| Произвольное K | 48,497122345 мс + K·56,000560 нс | (W−K)·56,000560 нс |
| K=W, включая допустимые повторы/накопление | 77,857543946 мс | 0 |

При **одном фиксированном новом календаре** `s_2m=2gm`, `s_(2m+1)=2gm+c`
с c=164ξ период посещения каждого слова `P=Wgξ` одинаков у E и безусловной
записи. Экономия периода — **0**, даже если CPU использует освобождённые хвосты.
От первого start до последнего release один конечный проход заканчивается на
`(Wg−2g+c+release_last)ξ`; меняется лишь **последний** хвост на 56ξ,
не W хвостов. Компактный последовательный проход без CPU мог бы приблизить
длительность к сумме busy, но это другой календарь/фаза/интервалы, сейчас
не предлагается как сертифицированный сервис. Старые P=73,400320 мс (3)
и 68,681728 мс (2,5) — номинальные периоды прежней модели, не нового backend.

Старый c=100 не подходит: даже ERR=0 с запасом и J не помещается
(дефицит 2,252012 нс); ERR-ветвь пересекает следующий start на 49,002480 нс
в достаточной проверке углов. Замена c на164 при прежних g=140/131 также
даёт перекрытие пар. Это отказ **данной циклограммы на старом календаре**.

Для последующего пересчёта проверен ресурсный пример, не выбран новый метод:
q-aligned g=208, c=164, read-charge r=104, неизменный условный X (`C_X=10⁻⁴`,
`σ_X=100 нс`). Пусть `M(h,p,d)=floor(h/p)*d+min(h mod p,d)`.
Для любого положения физического окна h=1 мс:

- all-ERR верх занятого времени: `M(h,2gξ_min,2cξ_max+J)`;
- только чтения: не более `2M(h,2gξ_min,rξ_max+J)`, ограниченного all-ERR верхом;
- при известном числе K_I исправлений, **пересекающих** окно,
  верх — минимум all-ERR и read-upper+`K_I(c−r)ξ_max`.

Выражения учитывают ±0,25 нс каждого края; J добавляется к длине покрытия,
а не маскируется новым частотным допуском. Времена r/c уже содержат 10%.
Прибавка X к доле — `C_X+σ_X/h`; добавлять ещё 10% к готовому результату
не требуется. Фазовый максимум маски точный при заданном period/duration;
сочетание min/max часов и сумма двух read-масок дают достаточный верх.

| Ресурсный пример | Верх в любом окне 1 мс, включая X | Остаток до 80% |
|---|---:|---:|
| g=208, K_I=0 в расширенном окне | 50,264100032% | 29,735899968 п.п. |
| g=208, исправляется каждое посещение | 78,992188512% | 1,007811488 п.п. |
| g=204, та же достаточная all-ERR оценка | 80,536353936% | −0,536353936 п.п. |

При g=208 P≤109,052994519 мс. Первый проход до release заканчивается не позже
109,052835017 мс без ERR или 109,052891018 мс при all-ERR; период остаётся тем же.
Это **ресурсная** иллюстрация, не проверка Q(T), ≤1% спокойной загрузки или
≤3 мкс задержки. Неуспех оценки g=204 не исключает другие оценки/исполнения.
X и полезная нагрузка ещё требуют пересогласования, g=208 не передаётся как
готовая рабочая точка для любой защиты. Новая сетка риска не выполнялась.

Дополнительный адресный контрпример: при g=208 после фактического all-ERR
release свободны лишь 16ξ и 104ξ до следующих фиксированных start.
Даже без ERR свободны лишь 72ξ и 160ξ. Данная фиксированная циклограмма
атомарного чтения 32 data занимает 184ξ (два read по 92ξ): её **нижняя**
длительность 184ξ_min−J=183,498160 нс больше **верхней** длительности
наибольшего no-ERR промежутка 160ξ_max+J=160,501600 нс. Уже начальный
сплошной проход S может задержать такой запрос более 3 мкс.
Это сравнение реальных интервалов выбранной циклограммы, не использование
верхней оценки WCET как нижней границы для любой реализации.
То есть успешная оценка пика сама по себе **не даёт** задержку ≤3 мкс.

| Запрос приложения | Нужный charge, ξ | Помещается при g=208 | Достаточное g на сетке 4 для одного промежутка |
|---|---:|---|---:|
| Read16 без inline repair | 104 | Да | 208 |
| Read16 с inline repair | 164 | Нет | 240 |
| Read32 атомарно, без inline repair | 208 | Нет | 260 |
| Write32 атомарно | 152 | Нет | 232 |

Последний столбец следует из `2g−c−148≥charge`, не является выбором
календаря и не проверяет поток/задержку/Q(T). Нельзя устранить контрпример
молчаливым дроблением атомарного 32 или снижением полезного потока.

Пока нет детерминированного K_I, допустимо K_I вплоть до всех посещений.
Ремонтная очередь=1 запрещает накопление отложенных работ, но не последовательные
ERR, повторный счёт или плотный всплеск в массиве. Один плотный миллисекундный
всплеск за 10 лет имеет ничтожную среднюю долю и всё равно определяет пик.
Считать только ERR, начинающиеся внутри календарной миллисекундной корзины,
нельзя: есть carry-in. Новая вероятностная квота на число исправлений не вводится.

## 6. Передача теоретику и точные оставшиеся входы

`handoff.json` содержит SHA T95/A/T90/T88, 14 закреплённых blob, два исхода,
все временные точки/единицы, оба прежних environmental/mark/quota договора
и отдельные D*: **3 → 560489/2000000000; 2,5 → 109073/2000000000**.
Параметры Λ/Θ копируются из закреплённых effective_T88_input без изменения.
Ни D*, ни ε=10⁻³, ни миссионные квоты, ни запас 10% не уменьшаются.
Старые c/g/ka/lead в handoff помечены baseline, не новыми сервисными входами.

| Изменение против T95/А | Что требуется от согласованного пересчёта |
|---|---|
| E вместо clean-U; read observation на60ξ, окончание write/release132–148ξ | Момент обслуживания и события внутри операции, исходный full38/ERR и δ_svc. Контрпример: latch чист, попадание на61ξ, записи нет, на92ξ слово грязно |
| Joint operation90,908… → условно148,501480 нс, charge164ξ; read-charge104ξ | Фаза, начальный проход, обязательность, интервалы, края конечного горизонта; никакого механического переноса старого Q(T) |
| Application/X atomic45 нс → таблица ширин/политик выше | Сохранить полезный поток, вывести новый work-envelope и очередь, сроки от первого VALID; read32 не один ×16 |
| Bounded edge error и полные CDC/командные пути | Совместимость с постоянным масштабом; сроки freeze/apply, LOW/hold/lease без расширения и поздних пропусков |
| E и у постоянного соперника | Новый допустимый соперник и обоснованная нижняя цена его класса; прежний full-U множитель выигрыша неприменим |
| Освобождение интерфейса по исходу | Полная спокойная цена с возвращениями/потерями; прежний общий U_M, без перезапуска ε/K₀/J/α и отмены pending |

Конкретный запрос оставшихся инженерных входов (не заказ испытаний):

1. Подтверждение или замена **границ из §1**: FPGA/IO/плата, нагрузка и STA,
   совместные dispatch/decision, часы и jitter, IO disable; если хоть одна больше,
   пересчитать эту же параметрическую циклограмму. Нельзя назвать её физическим WCET сейчас.
2. Контракт полезного трафика: ×16/32, число/атомарность alias, inline repair
   приложения, b/ρ и work CPU/X, верх backpressure; привязка CPU-часов/CDC.
   До него общий предел3 мкс и16 мест не подтверждены.
3. В научной передаче сохранить условными grouping/full38/ERR, aperture чтения
   и записи, условия канала. Дополнительные физические кампании не запрашиваются.

Варианты для закрытия временного остатка: **(1)** подтвердить эти проектные
верхние границы для выбранной позже платформы; **(2)** передать большие
обоснованные границы и повторить тот же расчёт до научного согласования.
Предлагается сейчас передать условную таблицу теоретику с явными неизвестными.
При дальнейшем отказе для 2,5 отмечается граница установленной области; при отказе
также для 3 нужны мешающий параметр и до двух вариантов Ивану, без повышения 80%.

## 7. Проверки и граница результата

```sh
python -B experiments/t104-new-rtl-executor/run_budget.py
```

Python≥3.10, стандартная библиотека, offline, относительные пути, Windows/Linux.
**28 новых проверок**: pin/clock/skew углы, сокращение интервалов на один такт,
10%, направления, clobber/clean-fence контрпримеры, полное/частичное занятие,
скользящие фазы/ERR-pattern на малом случае, carry-in, недостаточность свободного
промежутка для атомарного 32, две защиты и неизменные
квоты/unknown. Перебор малой маски не объявляется формальным доказательством
RTL для рабочего W. Формулы покрытия маской обоснованы в §5.
До них повторяются **15 старых**, **49 А**, **71 T95**, без `--write`.
После собственной генерации `--write` проверяется обычный запуск; только новые
`outputs/budget.json` и `handoff.json` могут быть перезаписаны этим флагом.
Двадцать blob защищают принятые входы и исторический первый шаг.
Симуляции FPGA/STA/аппаратного WCET, десятилетней физической гарантии и
нового научного сертификата в этой поставке нет. PR #109 остаётся draft.
