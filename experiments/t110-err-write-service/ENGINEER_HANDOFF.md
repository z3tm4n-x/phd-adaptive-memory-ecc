# Адресная передача T110 → оркестратору и инженеру

**Вход:** проверенный T104 `36f0dab3cfb1e051b9480d02c5aae303e943ecfe`.
**Новая научная версия:** точный commit указан в PR #111; машинный контракт —
handoff.json. Одна адресная проверка изменённых утверждений; новую кампанию,
RTL/В/Г не запускать до решения автора. Старые А/T95 не редактировать.

## Что проверить по точному SHA

1. Повторить `python -B experiments/t110-err-write-service/verify.py` без
   `--write`. Ожидаются прежние 28+15+49+71 и новые 111, оба новых JSON совпадают.
2. Независимо проверить E-включение: виртуальное **начало**, снимок внутри
   чтения, немедленный ERR-ремонт, пересечение предшествующего интервала
   с H_j. Член X_E>0, jitter входит в полное H_j. Контрпример clean-read
   → dirty-release сохранён. Проверить, что временная циклограмма не
   объявлена доказательством full38/ERR/E-aperture.
3. Проверить группы 8 и FIFO: край первой/последней группы, переход периода,
   все ERR, чтение 32 целиком, конец ответа/CDC и first-VALID. Для пика
   используется **реальный** release 92/148, для возможности исполнения —
   резервы 104/164 и 208 с неизменным 10%. Резервированный 85,419% не назван
   фактическим пиком; фактический верх с X 77,6139%. Это целевой пункт рецензии.
4. Проверить LOW 515 и направленное окно/lease, две 4-тактовые внутренние
   защиты, своевременное обновление, DE/DM. Ошибка покрытия одна на весь срок.
   При поздней/плохой выдаче — S; малая цена требует прежнего верхнего
   договора плохих окон/доступности, безопасное поведение само её не даёт.
5. Проверить цену с токенами, возвращениями/глобальной плохой историей/X;
   constant E при том же сервисе/приложении и новые ячеечные lower.
   33,676% и 117/161 из full-U не используются. Для 2,5 разделить отказ
   адаптивного upper и отдельное доказанное исключение постоянного E-класса.
6. Проверить потерю в каждом положении: до первого LOW, после freeze skip,
   во время read/repair, на истечении lease и восстановлении. Сохраняются
   j/фазы, pending, принятые обязательства, absolute windows, K0 и квоты.
   Новый экономный combined→ERR-only переход не заявлен.

## Неизвестные входы и проверка фактического потока

Не подставлять нули: platform/IO/clock/CDC/STA, совместная logic,
E-aperture/полный ERR, мониторная нижняя/верхняя связь и доступность,
полезные ширина/частота/всплеск/атомарность, backpressure, CPU/transport WCET.
Значения в новой конфигурации — достаточные **проектные требования**, не измерения.

Для фактического приложения нужны (i) типы полезных транзакций и политика
inline repair, (ii) совместная огибающая количества с X либо отдельные
огибающие с обоснованием их композиции, (iii) максимальный backpressure,
(iv) огибающая работы X с диагностикой/восстановлением. Проверять от исходного
VALID, не прятать ожидание перед READY/CDC. Произвольные независимые потоки
с одновременными bursts по одному могут иметь bΣ=2 и **не пройти** данный
тест, хотя средняя доля мала. Точный фактический поток сейчас не предъявлен.

При выходе за область сначала сообщить конкретный член (6), а не уменьшать
полезную нагрузку или увеличивать FIFO как замену доказательству задержки.
Два адресных направления на решение автора: иной детерминированный арбитраж/
фазовый календарь при том же E с повторной оценкой; либо меньший доказанный
атомарный путь запроса/большее аппаратное параллельное обслуживание.
Ни один вариант здесь не выдан за уже реализованный. Для текущей условной
строки дополнительное разрешение на начало научного пересчёта не требуется;
принятие нового контракта/переход к RTL решает Иван после проверки.
