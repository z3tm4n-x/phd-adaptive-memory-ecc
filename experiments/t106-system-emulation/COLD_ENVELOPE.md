# Сценарий4: явная дополнительная строка внутри r4 — до запуска

15.10.2026, при сведении пяти строк обнаружено: исторический cold-config
задаёт48 запросов через20мкс. Это превышает входной joint burst1/rate10000
из theory/t135-demo-operating-point.md §1/6,§4 (не менее100мкс).
Успешные данные/ID/начало той трассы остаются фактом; она не подтверждает
условие огибающей. config, cold JSON/trace, старый summary не меняются.
Прежняя фраза CONTRACT о сохранении огибающей для4 слишком широка.
Научное принятие чужим решением не переопределяем; предъявляем отличие.

Варианты: просто выдать старую цену как r4 (неверно); изменить принятый
config/результат (не сохраняет историю); добавить допустимую реализацию
ТОГО ЖЕ холодного сценария (выбрано). Это не шестая научная кампания.

До её результата фиксируем: те же corrected startup/firmware ELF,
fullW/full38, карта, восемь исходных инжекций с прежними эпохами и seed,
те же48 read/write пакетов/масок/данных. Только интервал приложения1мс,
начало10мкс, конец опыта48мс. Получается по500 read32/write32 в секунду
на этом опыте, joint spacing1мс≥100мкс. Последний запрос47,01мс, после
горизонта ничего бесплатно не дренируется. Остальное время приложения
пусто. Начало чистое — отдельный опыт, не runtime reset миссии.

Используем уже проверенный новый стенд/потоковый вывод и сервис188160нс,
как в1/2/3/5. Это изменение модели задержки относительно исторических
161940нс явно фиксируется; не аппаратное время ARM. Runtime LOW на этом
холодном коротком окне невозможен по исходному NR, его отсутствие проверяем.
Оба режима имеют одинаковый новый вход, каждый свои ERR.

Независимая проверка — check_burst с полными memory/app/ID/pin/history
свойствами. Python-подмена builder относится только к входу стенда;
она не меняет controller/C/RTL. Wrapper+конфигурация+проверки записаны
в source hashes. После успешной проверки новая строка идёт в общую
таблицу цены, прежняя показывается отдельно как нагрузочный cold-свидетель.
Q(T), заводская ECC-карта и время физического ARM не выводятся.
