# Контракт малого прототипа: слово, команда, сервис

Это спецификация и Python-проверки Research Engineer; реальный RTL не исполнялся.
Выбран один профиль 48-bit/39-bit/360 ns. Периоды резервов 1 и 0.5 с нельзя
переключать посреди миссии без нового согласованного состояния и бюджета.

## Слово и наблюдение

Каждый кадр: слоты 0...3 для чтений приложения, 4...7 для RMW скраббера.
Читается полное кодовое слово, результат декодирования защёлкивается, в конце
кадра всегда записывается исправленное полное слово. C_total увеличивается
ровно при завершённой записи слова, для которого было найдено одиночное
исправление. Data/parity — отдельная диагностика; C_total=C_data+C_parity.
Parity positions={1,2,4,8,16,32,39}; правило «первые 32 позиции — данные» неверно.
При незавершённом проходе новый полный snapshot не выдаётся. Отдельно считаются
started/completed passes и частичные reads/writes; pass_count старого RTL
считает запуски и не заменяет число завершений.

Snapshot содержит epoch, generation, profile, last_done, C_total и status.
Команда содержит epoch/generation/profile, период и абсолютный следующий конец.
Исполнитель возвращает ACK с фактически зафиксированными периодом/концом;
отклонение команды оставляет заранее обеспеченный резерв. Целостность записи,
пересечение тактовых доменов и надёжность ACK — условия будущего интерфейса,
не доказанные свойства Python-класса.

## Поздняя команда и продолжение

В t=last_done резерв уже определяет конец t+tau_b и начало t+tau_b-P.
Допустимая новая команда поступает не раньше snapshot и не позже этого начала,
имеет правильные теги, tau>=tau_b и end=t+tau. На равенстве deadline
спецификация отдаёт приоритет корректной команде; реализация обязана повторить
это или выбрать более ранний deadline. Дубликат отвергается. В конце H
не выполняется искусственный завершающий проход: учитывается только выполненная
часть операции, состояние не объявляется clean.

Программный слой не фиксирует новый slack при отправке команды. После ACK он
использует Delta_ACTUAL и observation kernel ACTUAL с полной длительностью от
предыдущего done, а не длительностью от ACK. Трасса checks_budget.py намеренно
сравнивает эти варианты: выполнение резерва после отклонения tau=2 не даёт
права обновить фильтр по ядру tau=2. Значение C получено собственным чтением
и исправлением инъецированных ошибок разных слов, не импортировано из истории
другой политики. В этой короткой конструкции нет повторных попаданий/MC.

Для актуального узла j запас s'_j=s_j-Delta_ACTUAL,j. Тождество
 q*r + E[q_next*V_remaining+s' | history] = q*V_current+s
сохраняется при выборе прошедшего проверку действия или прежнего резерва.
ACK/latency не должны зависеть от неразрешённых будущих ошибок/скрытого режима.
Конкретные проверки используют заранее заданные опоздания; произвольный
канал отказов связи или новый информативный датчик этим не сертифицирован.

Если snapshot потерян, разрешён постоянный уже обеспеченный резерв до H без
возобновления адаптации. Математическое скрытое обновление по ненаблюдённым
counts может существовать в доказательстве, но реальный контроллер не получает
из потери новый бюджет. Возобновление допустимо только после восстановления
всего упорядоченного журнала действий/counts. Потеря памяти/контроллера, срыв
самого обслуживания либо ложный ACK требуют отдельной модели и не покрыты
RMW guard. Пустое D-set относится к оплаченному механизму исключения, а не к
условной гарантии надёжности для каждой такой истории.

## Граница приложения

Пусть физический сервисный слот d=45 ns, кадр 8d. В каждом полном кадре
доступны четыре последовательных чтения приложения. При отсутствии иных
задержек/мастеров и FIFO этот периодический сервер допускает консервативную
rate-latency кривую beta(t)=R*[t-T]^+, R=1/(2d), T=8d.
Обоснование: интеграл доступного времени на интервале t не меньше t/2-2d: 
первообразная отклонения периодического сервиса от 1/2 имеет размах 2d.
Отбрасывание двух частично пересечённых краевых слотов теряет не более 2d.
Поэтому число полностью завершённых доступных слотов не меньше t/(2d)-4,
то есть R*(t-8d); отрицательная часть заменяется нулём.
8224 точных рациональных случая — численные witnesses, не замена этого основания.

Для любого входа с arrival bound alpha(t)=8+r*t при r<=R горизонтальное
расстояние между alpha и beta не превосходит T+8/R=1080 ns. Самих средних
10%/50% недостаточно: требуется ограничение пакетности на всех интервалах.
При дополнительном декодировании, wait states, арбитраже или очередях этот
bound не переносится без их верхних задержек. 100 us — исследовательский допуск,
не фактическое требование бортового приложения.

Для одного пакета 8 слов целые фазы дают 16d=720 ns, но приход сразу после
начала первого из четырёх доступных слотов теряет этот слот. Три чтения в
текущем кадре, четыре в следующем и последнее в третьем дают супремум 17d=765 ns.
Это не опровергает bound 1080 ns. Четверть-слотовая проверка даёт 753.75 ns.

При непрерывном fluid-входе 0.8C, C=1/d, на проходе доступно 0.5C, после него C.
Если a — время прихода от начала прохода P, виртуальная задержка:

    w(a)=0.6a                         при 0<=a<=0.625P,
    w(a)=0.5P-0.2a                    при 0.625P<=a<=P.

Максимум 0.375P=70.77888 ms достигается при a=0.625P=0.1179648 s.
На конце прохода только 0.3P=56.623104 ms. Это точные следствия указанной
fluid-аппроксимации постоянной нагрузки, не границы для пакетного RTL-арбитра.
Малый средний duty скраббинга сам по себе не обеспечивает deadline 100 us.

## Непроверенная реализация

В среде нет iverilog/vvp/verilator/yosys/Vivado. Новая RTL-симуляция, размещение,
измерение pins/bandwidth/CPU WCET не выполнены. 5 ns в config — целочисленная
сетка спецификации, не доказанный FPGA clock; старый OOC не подтверждает новый
48-bit порт, новую шину, phase timing или доступ к 36.44 MiB таблиц.
Нужен малый backend-тест только latch/слота/snapshot/ACK, а не полное портирование.
