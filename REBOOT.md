# Перезапуск исследования (v2.2): что и как

**Уточнение PI от 23.09.2026:** написание главы (W1 / #33) отложено.
Приоритет — сильный научный результат, его применимость и инженерное следствие;
изложение — после отдельного решения автора. Рабочая фиксация постановок,
доказательств и проверок продолжается. Актуальная очередь — в MAP и STATUS.

## Что изменилось в v2.2

- **Ядро работы задано паспортом:** метод управления по доступным наблюдениям с вероятностной гарантией на всём горизонте, область его применимости и целесообразности, оценка реализуемости. Ценность информации и активное наблюдение — способы улучшить или объяснить результат, а не новые обязательства.
- **Развилка G1 выбирает следующее ограниченное исследование,** а не центр диссертации. Если итог неясен — доводим принятое ядро и его текст.
- **Постановка G1 строже.** Метрика стоимости, информационные классы и сертификат определяются заранее. Разложение потерь исправлено. T2 может дать интервальные оценки или итог «причины не разделены».
- **Исключение класса** — только доказанная невозможность выполнить ограничения: F_LB > ε (строго) или несовместимость требований.
- **R0 — проект нового опорного сценария** с проверкой согласованности. Старые результаты на него автоматически не переносятся.
- **Пересказы итогов v1 уточнены:** у каждого числа — область применимости и статус.
- **Лимиты ограничивают затраты, а не истинность.** Правила про развилки и связь с железом смягчены.
- **T0:** теги проверяются по SHA, материалы переносятся с зависимостями, удаление веток — не условие начала работы.
- **Роль автора** описана отдельно от координации.

## Зачем перезапуск

v1 дала принятые результаты: RES-001…004, условные результаты по CY62167, проверки на реальных данных. Но за четыре недели в ней накопилось 350 коммитов и 111 веток, итоги разбросаны по невлитым веткам, а текста диссертации нет. Это проблема интеграции и оформления, а не бесполезности работы.

Перезапуск нужен, чтобы завершить и объединить накопленное, а не обнулить v1. Цель — довести результат до связки «утверждение → доказательство → сравнение → реализуемость → текст».

Честность, строгие доказательства, воспроизводимость и готовность признать отрицательный результат остаются.

## Как работает v2.2

- **Одна карта.** `MAP.md` — что нужно для защиты, критерии готовности, статус. Задача либо помогает выбрать действие, либо закрывает конкретный критерий карты.
- **Недельный ритм.** Понедельник — план, не больше трёх задач агентов. Пятница — итог, слияние, `STATUS.md`.
- **Опорный сценарий** — R0 в карте.
- **Строгость по важности:** разведка / для диссертации / для статьи или положения.
- **Лимиты затрат:** задача до 5 дней, одна рецензия и одно исправление. Дальше — принять, сузить утверждение, сохранить как незавершённое или прекратить.
- **Решения за тобой:** два варианта и рекомендация.
- **Передача через GitHub:** задача — Issue, работа — ветка, итог — PR.

Подробно — `agents/00_RULES.md`.

## Твоя роль

**Координация — около трёх часов в неделю:**
- в понедельник утвердить план;
- принимать решения;
- в пятницу посмотреть итоги и слить PR;
- обеспечить внешние входы: COSRAD, данные, плату ПЛИС;
- раз в месяц сверяться с научным руководителем.

**Авторство — отдельно и главное.** Ты автор диссертации. Агенты ускоряют работу, но не заменяют тебя. Поэтому нужно:
- понимать постановки и ключевые доказательства настолько, чтобы объяснить их руководителю и совету;
- проверять постановку задачи до расчёта;
- читать ключевые работы из обзора;
- к каждому принятому результату уметь кратко изложить суть своими словами. Для этого в каждом PR есть раздел «Суть для автора».

## Запуск по шагам

1. **Положи файлы в репозиторий.** `agents/`, `.github/`, `MAP.md`, `STATUS.md` — в корень. В начало `docs/agents/README.md` добавь строку: «Устарело. Действующие инструкции — в `agents/`».
2. **Защити main.** GitHub → Settings → Branches → правило для `main`: изменения только через PR.
3. **Дай доступ.** Codex — запись в ветки. Оркестратору и писателю — GitHub-коннектор.
4. **Запусти оркестратора** стартовым сообщением ниже.
5. **T0 «Рабочий набор и R0»** (инженер): теги на все ветки → проверка по SHA → перенос нужных материалов с зависимостями → таблица согласованности R0. Удаление старых веток — позже, начало работы от него не зависит.
6. **Параллельно, не блокируя G1:** COSRAD по `experiments/RE-INTERNAL-COUNT-COSRAD-GOES-01/COSRAD_REQUEST.md` (ветка `research/internal-count-cosrad-goes-01`).

Команды для T0 — для справки, их выполняет инженер (Git Bash):

```bash
git fetch --all
git tag v1-archive origin/main
for b in $(git branch -r | grep -v HEAD | sed 's#^ *origin/##'); do git tag "v1/$b" "origin/$b"; done
git push origin --tags

# проверка по SHA: пустой вывод — всё сохранено верно
git ls-remote --tags origin > remote-tags.txt
for b in $(git branch -r | grep -v HEAD | sed 's#^ *origin/##'); do
  want=$(git rev-parse "origin/$b")
  got=$(awk -v r="refs/tags/v1/$b" '$2==r {print $1}' remote-tags.txt)
  [ "$want" = "$got" ] || echo "НЕ СОВПАДАЕТ: $b"
done

# перенос материала: берём состояние ветки для нужных путей, а не последний коммит
git checkout -b t0-working-set origin/main
git checkout "v1/<ветка>" -- <путь1> <путь2>
```

Для каждого перенесённого материала в PR T0 — строка таблицы: материал, тег, SHA, пути, зависимости (код, входы, тесты, рецензия, решение о принятии).
